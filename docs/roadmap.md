# Cadence — Status, Risks, and Backlog

Where the project actually stands, what is known to be unverified, and what is proposed next. Design lives in [architecture.md](architecture.md); model choices and measurements live in [benchmarks.md](benchmarks.md).

## V1 scope

Tauri + React/TypeScript · Windows microphone enumeration · recording · local storage · local STT · local speaker diarization · English/Tamil code-switching · speaker-labelled transcript · local LLM · structured MoM · meeting history · in-meeting transcript search · timestamp-linked playback · Markdown/JSON export · model management · progress and status · failure recovery · no cloud runtime dependency.

**Explicitly out of V1:** cloud transcription · cloud LLM · real-time captions · face recognition · voice biometric identity · automatic real-name recognition · cross-meeting RAG/search · calendar integration · Teams/Zoom integration · mobile or web client · remote backend · multi-machine processing · cloud backup. Keep interfaces extensible, but do not build these early.

## Status

The recording → transcript → MoM path is implemented end to end, entirely on the laptop, including history, export, a catalog-driven Model Manager with a consent-gated first-run setup, and a single model set (Whisper small + Qwen3-8B) that every machine runs, with a 16 GB minimum. **On 2026-11-19 a real recording went through the app itself for the first time**: a 28 s meeting from a laptop's built-in mic array, on a 16 GB i7-1260P, recorded and processed to a transcript through the UI. Minutes were not generated, because the LLM RAM preflight refused them (risk 14). A recorded meeting produces `original.wav`, `processed.wav`, `diarization.json`, `stt.json`, `transcript.json`, `mom.json`, `audio_profile.json`, `classification.json`, `redaction.json`, and `metrics.json` under `%APPDATA%\com.cadence.app\meetings\<id>\`, with no network involved.

## Open risks

Security review (2026-10-05): hardened meeting filesystem access, enabled a production webview CSP, and restricted model download transport to HTTPS without inherited curl configuration. Regression tests cover these guards. This does not close risk 5 (unpinned upstream model hashes) or replace clean-install and real desktop smoke testing.

Follow-up: recording now atomically refuses existing `original.wav` destinations instead of truncating them. Expanded regression cases cover Unicode compatibility, junction/path boundaries, model integrity, and CSP isolation between production and development.

These are carried forward deliberately rather than closed by assertion.

1. **Compiles and tests pass, but has not been exercised on a real meeting end to end.** `cargo build`, `cargo test` (unit tests plus the 15 offline-guarantee integration tests) and `npm run build` all succeed. That is not the same as the pipeline having been run against real audio in the app — which remains unverified. *Narrowed (2026-10-05):* the shipped pipeline code up to the transcript has now run on real speech, outside the app, through `bench_cli compare` and the `baseline` test — but minutes were not generated (risk 17), and a public broadcast clip is not a meeting recorded on a laptop mic in a room.

    *Narrowed again (2026-11-19): the app has now recorded and transcribed a real meeting, but has not summarised one.* Under `npm run tauri dev`, driven through the real UI on the 16 GB i7-1260P, a 28 s recording from the laptop's built-in Intel mic array was captured (level meter live; the low-signal warning fired correctly in a quiet room) and processed to a transcript — preprocess → GTCRN → Silero VAD → diarization → STT → align → classification → redaction scan — in ~45 s, and ~58 s on a re-run, with every raw artifact kept. Minutes were refused both times by the RAM preflight (risk 14), which surfaced as a visible, recoverable warning with "Generate minutes" to retry. What remains unexercised in the app is the minutes stage. And 28 seconds of one person in a quiet room is not a meeting: no long recording, no multi-speaker room and no packaged build have been through it.
2. **No sized benchmark has ever been executed.** The whisper model size and the choice of Qwen3-8B are unvalidated defaults. The diarization cluster threshold now has a small threshold-sweep result (two conflicting samples, `bench_cli diarize`) but still needs labelled 3/5/10-speaker recordings to settle for real. The first WER exists — 16.7% on one English broadcast clip against all-caps, non-verbatim live captions, so an upper bound, and 2.8% on the TED talk against professional captions — which says `whisper-small` is not broken on English, not that it is the right size. See [benchmarks.md](benchmarks.md).
3. **No Tamil or code-switched audio has been through the pipeline**, though mixed English/Tamil is a hard V1 requirement. This now blocks judging MoM quality on Tanglish content, not just STT accuracy. The caption-referenced baseline (2026-10-05) does not help here yet: both clips are English, and no Tamil or Tanglish recording with human captions has been found to add. The language mix the product exists for is still untested on real audio, and the baseline cannot catch a regression in it.
4. **Processing time may miss its target.** The one small sample extrapolates to roughly 15 minutes for a 60-minute meeting, against a 10-minute target — and that was measured before the LLM stage existed. Since then two costs have been added knowingly: the model-free noise reduction now defaults **on** (risk 15), and the LLM is now the 8B on every machine (risk 14). Neither has been timed on anything. One new data point, from a different machine (16 logical cores, 16 GB — not the i9-13950HX behind the other figures): STT on the 2:15 baseline clip ran at 0.53x real time with 16 threads, against the i9's 0.11x (24 threads) on the 57.4 s sample. Extrapolated naively, a 60-minute meeting's STT alone would take ~32 minutes on that machine — three times the whole pipeline's target. If target machines look more like it than like the i9, this risk is not "may miss" but "misses". (That 0.53x, like every STT figure in this risk, was measured while whisper.cpp was unknowingly loading llama.cpp's newer ggml. See the 2026-11-19 update.)

    **Update (2026-10-06): that machine is an i7-1260P (hybrid, 4 P + 8 E cores, 16 logical, 16 GB), and threads will not rescue it.** A quiet-machine sweep on a 2:00 excerpt ([benchmarks.md](benchmarks.md#thread-scaling-on-a-hybrid-laptop-cpu-i7-1260p-2026-10-06)) found STT flat from 4 to 16 threads (~50 s, ~0.42x), because beam-search decoding is ~25 s — half of STT — at every thread count; diarization flat from 2 to 8 and worse past it; and the LLM (Qwen3-4B stand-in; the 8B is still unmeasured) fastest at the P-cores' 8 logical threads on a realistic 3.2K-token prompt — 12–13 tok/s prefill and 4.6 generation, against 10.8 / 3.0 on the old default of 14. The LLM default now follows the P-core count on hybrid CPUs (`settings::default_llm_threads`); the i9 is unchanged at 16. **The bigger finding is where the time goes: prefill at ~12 tok/s makes each ~5K-token chunk 6–7 minutes before generation starts**, so on 16 GB laptop-class hardware it is minutes generation, not STT, that puts a 60-minute meeting far outside the target — and that is projected from the 4B, not the heavier 8B that ships. The full 11:44 TED clip agrees: 600.7 s to the transcript (0.85x), then 7,042 s for minutes at 14 threads (with concurrent builds inflating it). The levers left are decode strategy for STT and prefill configuration for the LLM (backlog), and if neither is enough, the 5–10 minute target does not hold for this hardware class, and either the target or the minimum machine has to change.

    **Update (2026-11-19): STT is now ~32% slower, deliberately, and every earlier STT timing was flattered.** All three runtimes used to be flattened into one shared `<models>/bin/`. whisper.cpp (b4938) and llama.cpp (b10717) both ship `ggml.dll`, `ggml-base.dll` and `ggml-cpu-*.dll`, so whichever installed last won. On the i7-1260P, whisper.cpp had been running on llama.cpp's newer ggml, working by ABI luck, and every STT figure in this document and in [benchmarks.md](benchmarks.md) was taken that way. Each runtime now has its own folder ([architecture.md](architecture.md#runtime-layout)). That is the correct fix, and it means whisper.cpp now loads the older ggml it shipped with. A controlled A/B on the 2:15 council clip, with the same `whisper-cli.exe` and model and alternating runs, gave 56.2 / 55.2 s on the borrowed ggml and 73.6 / 73.9 s on its own: about 32% slower, with byte-identical transcripts ([benchmarks.md](benchmarks.md#runtime-isolation-and-the-first-in-app-run-2026-11-19)). The TED baseline agrees (STT 786.3 s against 587.1 s recorded, under noisier conditions). The recovery is not to share DLLs again. It is to move whisper.cpp to a release whose bundled ggml is current (backlog: whisper.cpp b5454), which needs the owner's sign-off and a baseline re-run.
5. **Model integrity is trust-on-first-install.** No pinned upstream hashes; a digest recorded at install time cannot detect a download that was already compromised. Worth hardening before packaging, especially on machines running enterprise EDR.

    *Partly mitigated (2026-11-20): for the runtimes, not the models.* The three runtimes no longer download at first run. `scripts/prepare-runtimes.ps1` bundles them into the installer, and it refuses any release archive whose SHA-256 differs from a pin in the script ([release.md](release.md)). The installed app's Verify checks every bundled file against a manifest written at build time. The pins were taken from fresh downloads and cross-checked against the digests the app had recorded for its own downloads of the same releases the day before. All 54 shipped files matched. That is two downloads agreeing, not upstream attestation: none of the three projects publishes checksums, so a release that was already compromised when first fetched would still be pinned as-is. **What remains:** model data (Whisper small, Qwen3-8B, the diarization, GTCRN and Silero models) is still trust-on-first-install, with no pinned hashes, and that is the bulk of the bytes. A development build without bundled runtimes still downloads unpinned runtimes the old way.
6. **No one has run a meeting with the network actually disconnected.** *Narrowed, not closed.* `src-tauri/tests/offline_guarantee.rs` (15 integration tests) now proves the structural half automatically: no HTTP/TLS/telemetry/cloud-SDK crate is linked, the only absolute URLs in crate source are the model catalog's, the only socket-opening module is the loopback client, the frontend issues no requests, the Tauri config grants no network capability, and nothing pulls in a Python runtime. What that cannot establish is that the app *works* with the adapter disabled — whether Windows, WebView2, WASAPI, the SQLite VFS, whisper.cpp, llama.cpp and sherpa-onnx all behave when name resolution fails and the default route is gone, and whether every model is present locally. No test process can answer that. **What remains open is one manual check: a human doing a full record → process → MoM cycle on a machine with the network adapter disabled.** It stays here until someone has done it. (A finding worth keeping: `Cargo.lock` contains `reqwest`, `hyper` and `tower-http` as optional Tauri dependencies that this feature set never enables, and `cargo tree` shows none of them linked — which is why the test reads `cargo tree` and not the lockfile. A lockfile check would fail today for no real reason, and the natural "fix" would be to allowlist `reqwest`, permanently defeating the check.)
7. **Every audio and classifier default is an unvalidated guess.** The leveler's range, window and time constants (validated on synthetic signals only), the compressor's threshold and ratio, the noise-reduction strength, every threshold in the noise classifier, the arithmetic behind the audio quality score, and the meeting-type cue weights were all reasoned about and none were measured. The stages are unit-tested for mechanism, not for being right on a real recording. A "fair" quality grade currently corresponds to no known amount of transcription accuracy. See [benchmarks.md](benchmarks.md) for the per-default list and what would settle each.
8. **The shipped lexicon covers English profanity only, and contains no slurs by design.** A public source repository should not carry a list of racial, religious, caste, sexual-orientation or disability slurs, so it does not. The `slur` category is wired through the matcher, the flag shape, the summary and every rendering mode — only the terms are absent, and an organisation populates them through the override file at `%APPDATA%\com.cadence.app\lexicon\en.txt`. That is also the right place for it on the merits: which words an organisation treats as unrepeatable in a circulated record is its own policy, not this project's. The practical consequence to state plainly is that **out of the box, Cadence does not detect slurs.**
9. **`ta.txt` and `ta-latn.txt` ship empty on purpose.** Romanized Tamil has no standard orthography — one spoken word has a dozen written forms, none of them wrong — and no Tanglish audio has been through this pipeline, so which forms whisper.cpp actually emits is not something the project can predict today. Neither the recall nor the precision of a guessed list could be stated, and short romanized Tamil strings collide with ordinary English words, so a guess would put false positives on innocent speech in a circulated record. **This is the same blocker as risk 3**: it is unblocked by real Tamil audio, not by more thought. The machinery is present and the lists are not, deliberately.
10. **Meeting-type classification is cued in English.** A meeting conducted mostly in Tamil falls through to `general` with low confidence rather than being mislabelled — the intended failure mode, since a wrong label is worse than no label, but it does mean the feature is currently English-only in practice. Topic extraction is language-agnostic term frequency and works regardless. Tamil cue profiles need the same audio risk 3 is waiting on, to build them against something.
11. **Masking the transcript does not mask the audio.** Redaction annotates text; `original.wav` is untouched and playback plays exactly what was said. The UI must say so rather than implying a meeting has been sanitized. A playback bleep is a possible later item, not a current property.
12. **The word-level alignment split has met real multi-speaker audio once, and needed a diarization fix (update below).** `align::speaker_pieces` can now cut an STT segment at a word boundary when the words inside it disagree about the speaker, which is what closes the "fast exchange collapses onto one speaker" limitation *in principle*. What was actually verified: word assembly against real `whisper-cli.exe --output-json-full` output (single-voice probes of the vendored binaries), and the splitting logic against constructed diarization intervals in unit tests. **Nobody has confirmed that sherpa-onnx's real intervals produce sensible word-level runs on a genuine fast exchange**, and neither existing sample has been re-run since the split landed. The 57.4s sample is the cheapest available check — its 30s back-and-forth collapsing onto one Person 1 turn is precisely the case this exists to fix — but nobody has done it. The design is fail-safe by construction (word timestamps can only split a segment, never re-attribute one that stays whole; a segment with no words takes the old path exactly), so the risk is a *wrong* split rather than a lost transcript. **No minimum-run-length heuristic was added, deliberately** — a floor would guess at a problem nobody has observed yet, and would trade a visible wrong label for a silent one — but that judgement is untested and undefended in the code. It is the first thing to watch if real intervals jitter at boundaries. See [benchmarks.md](benchmarks.md).

    **Update (2026-10-05): real intervals did jitter, and the fix went upstream of the split.** On the first real multi-speaker clip (2:15 council news report), sherpa-onnx emitted gapless ~1 s windows with different speaker ids inside one continuous voice; the split faithfully turned one anchor's opening line into Person 1→2→3→4→2 and the clip reported 10 speakers. Rather than a minimum-run floor on the split, `align::absorb_islands` now relabels short segments touching neighbours on both sides before attribution ([architecture.md](architecture.md)), leaving `diarization.json` raw. Still open: the trade-off that a genuine gapless back-channel is absorbed, the thresholds (`ISLAND_MAX_MS` / `TOUCH_GAP_MS`) resting on one clip, and the split still not having met a genuine fast *exchange* — a news report is mostly long turns.

    **Update (2026-10-06): a review of the alignment against the audio.** Two more fixes landed: `align::drop_nested` drops a segment under 1.5 s lying wholly inside an earlier one (sherpa-onnx's way of reporting overlapped speech, 0.3–0.5 s slivers that the island test could not see because their start-order neighbours are not their time neighbours), and the segment sort is now deterministic (start, longest first, speaker id), so the result never depends on the order sherpa-onnx wrote the file in. On the council clip, shipped front end at threshold 0.5: turns 44 → 29, speakers 10 → 9, turns under 2 s 25 → 9, mid-sentence speaker flips 29 → 18 (raw front end: turns 33 → 19, flips 20 → 11). Better, not fixed — 18 flips remain, and the speaker count is still above the plausible 6–9 for that clip, which is as much risk 18's threshold problem as an alignment one. The accepted cost is unchanged: a gapless back-channel under 1.5 s is absorbed.
13. **Masking the MoM model's input costs signal, by an unknown amount.** Under `mask` or `redact`, `mom::mask_for_grounding` hides flagged spans before chunking, so a heated exchange reaches the extractor as `b****`. That is the intended trade — minutes circulate, and a model that never sees the word cannot quote it back — but it has never been run against a real model, and **no meeting audio containing flagged language has been through this path at all**. Whether the shipped model reads a masked token as "there was heat here" or lets a run of asterisks derail a chunk into contentless facts is unknown. Mitigating but also untested: the v2 prompts tell the model to carry masks through rather than guess at them, and `flag` — the default — hides nothing.
14. **Qwen3-8B on a 16 GB machine is unmeasured, and it is the top risk.** Memory tiering was removed: every machine now runs Qwen3-8B Q4_K_M at 8K context, and the minimum is 16 GB. The 8B has **never been run on any machine here**. Its fit rests on an estimate — ~4.8 GB of weights, ~0.66 GB of q8_0 KV cache, ~0.6 GB overhead, about 6 GB against a 7,000 MB advisory budget, with `preflight_memory` wanting ~7.5 GB *free* before it starts. Unknown: peak RAM in a real run, generation time for a 60-minute meeting, and whether it fits alongside Windows, the webview and the page cache on a real 16 GB laptop at all. The only measured LLM number is the q8_0 KV saving (~540 MB, on Qwen3-**4B**), and its effect on minutes quality is itself unmeasured. If it does not fit, the recovery is a smaller single model for everyone, not a return to tiers. The transcript is safe either way — a preflight refusal only defers the minutes.

    **First real data point (2026-11-19): on a real 16 GB laptop with ordinary apps open, the preflight blocks the 8B.** The in-app run (risk 1) on the i7-1260P (16,008 MB total) reached the minutes stage twice and was refused twice: 4,921 MB free the first time and 6,079 MB the second, against the 7,550 MB the check needs (6,050 MB estimated for Qwen3-8B Q4_K_M at 8K context, plus 1,500 MB headroom). Settings showed 1.0 GB free at one point. The refusal behaved as designed: a visible, recoverable warning, the transcript untouched, and "Generate minutes" to retry. Its message now states the threshold and the shortfall ("…Close other applications (browsers especially) to free at least 1471 MB more…"); the threshold itself is unchanged. What this does **not** show is whether the 8B fits once started (the check is an estimate, not a measurement), how much RAM it actually peaks at, or how long it takes. **The 8B has still never run on any machine here.** The only part of llama.cpp exercised from its own folder is `llama-server.exe --version` (build 10717). What it does show is that a 16 GB laptop in ordinary use does not have 7.5 GB free. Either users are told to close their browser before minutes, or the threshold, the model or the minimum machine has to move. The next step is to measure the 8B with enough RAM freed, before choosing between those.
15. **Noise reduction is now on by default, at the cost of an STFT against the 10-minute target.** Model-free noise reduction used to be off because it is a full-recording STFT against risk 4's budget. It is now on as the fallback whenever GTCRN does not run — GTCRN still supersedes it, never both — so a machine with the full required set normally skips it, but a machine without GTCRN, or a run where GTCRN fails and the chain is re-run from `original.wav`, pays for it. That cost is accepted, not measured. See [benchmarks.md](benchmarks.md).
16. **Endpoint security may flag the first-run download.** First-run setup re-introduces a bulk download of executables and archives from GitHub/Hugging Face — the pattern commit `59ecece` removed because it read as dropper-like to endpoint security tooling. The mitigations are explicit consent over the full visible list, one download at a time on one thread, and a skip that lets recording proceed without it. They are mitigations, not a fix: **how any EDR product actually responds is untested.** Worth checking on a managed enterprise machine before packaging; risk 5 (no pinned hashes) compounds it. *What has been checked (2026-11-19)* is the flow itself, on an unmanaged machine. With GTCRN and Silero VAD moved aside, the app opened on the setup screen listing exactly those two (1 MB each); "Download and set up" installed them one after the other through the UI and handed over to the Record screen, and the re-downloaded files were byte-identical to the originals. That shows the consent flow works. It says nothing about EDR, so this risk is unchanged.

    *Partly mitigated (2026-11-20): no executable is downloaded at runtime any more, in a release build.* The pattern that most resembles a dropper — unsigned executables and DLLs fetched from GitHub into `%APPDATA%` and then run — is gone. The runtimes ship inside the installer, which is per-user (`%LOCALAPPDATA%\Cadence`, no admin, no UAC). Every bundled executable and DLL goes through the same signing step as the app (`scripts/sign.ps1`), and `npm run release` refuses an unsigned build ([release.md](release.md)). First-run setup on a release build downloads model data only. **What remains:** (a) **no signing identity has been obtained yet**, so every build so far is unsigned and none of the reputation benefit applies; (b) setup still spawns `curl.exe`/`tar.exe` to fetch model files from GitHub and Hugging Face, and **how any EDR product responds to that, or to the installer, is still untested** — a managed enterprise machine is still the test; (c) SmartScreen reputation for an OV-signed build builds up over downloads and cannot be had on day one, while EV or Azure Trusted Signing establish it faster without a guarantee; (d) no installer has yet been built from this configuration and installed on a clean machine.
17. **A machine upgraded from the tiered builds can keep a stale LLM.** *Mitigated in code (2026-11-19, update below); the missing 8B is now risk 14's problem.* The 2026-10-05 real-audio runs were on a 16 GB, 16-logical-core machine — exactly the box risk 14 needs — but it still had the retired Qwen3-4B installed and not the shipped Qwen3-8B, so minutes for the shipped model were not exercised and risk 14 stays where it was. Nothing told anyone: the setup screen reports the 8B as missing, but an installed-but-retired model is invisible — no longer in the catalog, so neither offered for removal nor flagged as dead weight on disk. `check_models` / the setup screen should name it. Related, and harmless but confusing: on that machine `models/manifest.json`, written by earlier builds, still records informational `file` paths under the pre-rename `%APPDATA%\com.echomind.app\…` folder, and nothing rewrites them. Lookups go by id and SHA-256, so nothing resolves through those paths, but anyone debugging a model install by reading the manifest is sent to the wrong directory.

    **Update (2026-11-19): both halves are handled.** `models_manager::find_retired` lists anything in a model folder that the current catalog does not own: a retired catalog file (Qwen3-4B, Gemma 3 4B, Whisper base or medium) by its model name, and anything else by its file name. `check_models` carries the list, so the setup screen and Settings → Models both show it (`RetiredModelsNotice`) with a Remove button behind a confirmation. Nothing is removed automatically, and removal is confined to the models folder. Stale `com.echomind.app` paths are rewritten to the current models folder whenever the manifest is next written (any install or removal); a manifest nothing has written since still carries them, harmlessly, until then.
18. **Diarization is unscored.** Neither baseline clip has a speaker-labelled reference, so there is no diarization error rate — only per-clip speaker-count ranges, which catch a collapse to one speaker or a shatter into ten, not a wrong attribution with a plausible count. The island fix (risk 12) was judged by reading one transcript. A speaker-labelled reference — a clip with per-speaker caption marks that can be trusted, or a purpose-made recording with known speakers — is what would let a cluster-threshold or island-threshold change be measured instead of eyeballed.

    **Update (2026-10-06): a threshold sweep on the council clip, re-aligned with the current `align`, confirms that no single cluster threshold serves every recording.** With the true count plausibly 6–9, transcript speakers went 9 / 7 / 5 / 4 / 3 at thresholds 0.5 / 0.6 / 0.7 / 0.8 / 0.9 (raw clusters 10 → 4; table in [benchmarks.md](benchmarks.md#diarization--sherpa-onnx)), so 0.5–0.6 suits a many-voice room — while a 2:00 single-speaker TED excerpt still gave 3 clusters at 0.5, and the earlier clean two-speaker sample collapses to one id above 0.5. Every one of those judgements is still made against a plausible range, not a label. What a threshold cannot do, more information can: an expected-speakers hint from the organiser, or a second pass that merges small clusters into their nearest large one (backlog).

## Backlog

Proposed, not scoped into a phase. Item 1 is the exception: two of its three tiers are now built, and it is kept here — rewritten to say what shipped — because the rest of it is still open.

### 1. Unparliamentary-language detection and masking — Tiers 1 and 2 shipped

Detect profanity, abuse and slurs in a transcript and mask them, the way an official record expunges unparliamentary words. Meeting minutes get circulated; a verbatim transcript of a heated discussion often should not be.

**The design decision that mattered most held: it never destroys the text.** Detection produces *annotations*, not edits. Each transcript turn carries a `flags` array — `{ start_char, end_char, term_id, category, severity, method }` — and `transcript.json` keeps the true text. Masking is applied at render and export time. `original.wav`, `stt.json` and `diarization.json` are never touched. That keeps the raw-artifact rule intact, makes the policy adjustable without re-running STT, keeps evidence timestamps valid, and makes a wrong flag reversible.

**Built (`src-tauri/src/pipeline/redact.rs`):**

- **Tier 1, the lexicon matcher.** Aho-Corasick over normalised turn text — hand-written rather than the `aho-corasick` crate, which the original sketch assumed: it is a hundred lines against a new dependency, and the alphabet here is Unicode rather than bytes. Normalisation folds case, leetspeak, repeated characters and in-word separators, keeping a map back to the original offsets so a match can be located and masked. Word-boundary matching plus a per-lexicon allowlist keeps the Scunthorpe problem in check.
- **Tier 2, tolerance for STT error.** Edit distance ≤ 1 for terms of 5+ characters, plus a phonetic key. **Gated to `severe` terms only** and off by default, as planned.
- **Terms as data.** `assets/lexicon/{en,ta,ta-latn}.txt` compiled in via `include_str!`, each entry carrying a category (`profanity | slur | sexual | violent | insult`) and severity (`mild | strong | severe`), with an override merged over them from `%APPDATA%\com.cadence.app\lexicon\` — the same pattern the versioned prompts use.
- **The four modes** — `off` · `flag` · `mask` (`f***`) · `redact` (`[expunged]`) — with `flag` as the default, since it is the only honest one for a matcher that cannot tell a quotation from an insult.
- A `redaction.json` summary per meeting, and a rescan command for after the lexicon or the setting changes.

**Tier 3 is deliberately not built, and should stay that way for now.** A small multilingual toxicity classifier exported to ONNX would run beside the diarizer at almost no architectural cost, and it would buy the one thing a wordlist can never have: context — an insult assembled from individually innocuous words, or a benign use of a flagged term. It is the right next step *if* Tiers 1 and 2 prove insufficient. The reason to wait is that **"insufficient" is not measurable today**: no Tamil or code-switched audio has been through this pipeline, so there is no way to say what Tier 1 misses. Adding a model, a catalog entry, a Model Manager row and another required download to close an unmeasured gap would be guessing with a download attached. When it is built, prefer ONNX over reusing the loaded llama.cpp model: an LLM classification prompt needs no extra download but is slower per run and non-deterministic, both wrong properties for something that must be auditable and reproducible.

**What remains open:**

- **The lists.** English profanity only; **no slurs, by design** (risk 8), and both Tamil files **empty on purpose** (risk 9). These are the two biggest gaps in coverage and neither is closed by writing code.
- **Recall and precision are unknown.** No transcript containing real profanity has been scanned. The unit tests use a synthetic fixture lexicon — real slurs are deliberately not committed to this repository — so they prove the matcher works, not that the shipped list is right.
- **Surfaces.** The rule is that every surface showing transcript text respects the mode. **Export is done and is the one that was hardest to get right**: it re-scans with the current lexicon rather than trusting stored flags, masks minutes evidence quotes and the flags' own `term_id` as well as the transcript, and has a test asserting the original word appears nowhere in the output. The in-app surfaces — transcript view, MoM evidence, and search (search the true text, display the masked form, or a flagged word becomes unfindable) — render from the flags the backend supplies and should be checked against the shipped UI rather than assumed.
- **MoM generation now respects redaction — untested against a real model.** `mom::mask_for_grounding` masks the transcript *before* it is chunked, rather than masking evidence quotes afterwards: an evidence quote is transcript text the model lifted verbatim, so masking at render time would be too late for anything the model chose to repeat back, and masking the input means every quote downstream is masked by construction. It **rescans with the current lexicon and unions with the stored flags** instead of trusting what is on disk, because `run_redaction` returns early in `off` mode — a meeting processed with redaction off carries no flags at all, and a user who then switches to `mask` and regenerates would otherwise get unmasked minutes with nothing showing anything had failed. It is **the one place in this pipeline that fails closed**: everywhere else a failing stage degrades to doing less, and here doing less means printing the words into a circulated document, so a missing or empty lexicon falls back to the built-in list rather than to no masking. The prompts moved to `extraction_v2` / `synthesis_v2` to carry the same contract in words (never reproduce offensive language; treat `f***` and `[expunged]` as deliberate masking to carry through, never to guess at or expand); v1 of both stays on disk and loadable, because existing `mom.json` files name the version that produced them. `MomMeta.redaction_mode` now records which mode a set of minutes was generated under, defaulting to a `"unknown"` sentinel — not `off` — for a file written before the field existed. **What is not done: any of it run on a meeting containing flagged language** (risk 13).
- **A playback bleep**, if masking is ever to mean anything about the audio (risk 11).

**Limitations that are accepted rather than open:**

- A lexicon has no context. Quotation, sarcasm and reclaimed usage will be misclassified sometimes; that is the cost of a deterministic Tier 1, and the reason `flag` is the default.
- **Per-speaker profanity counts stay out of scope.** The data makes them trivial; they would turn a transcription tool into a surveillance one and cut against the "never identify real people" rule. Build only on an explicit, considered request.
